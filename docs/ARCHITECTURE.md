# Архитектура Wuppertal Live

## 1. Общая схема

```
Cloudflare Cron (2 / 5 / 10 мин)
   └─► src/cron.js ─► источник (autobahn | nina | presseportal)
                          ├─ fetchWithRetry (таймаут 8 с, 2 повтора, ключи вырезаются из логов)
                          ├─ нормализация → единый формат события
                          ├─ geo.js (Nominatim, кэш в D1, ≤3 запроса за запуск, 1 запрос/сек)
                          └─ events.js: syncSource → D1 (UPSERT, детект изменений, завершение)

Браузер (GitHub Pages) ─► Worker /api/events, /api/status (Cache API 20–30 с) ─► D1
Админ ─► Worker /api/admin/* (Bearer ADMIN_TOKEN)
```

Frontend не содержит секретов и сам ничего не вычисляет про актуальность: статус приходит с сервера и расшифровывается в интерфейсе.

## 2. Единый формат события (таблица `events`)

| Поле | Смысл |
|---|---|
| `id` | `<источник>:<хэш source_event_id>` — стабильный, поэтому дублей нет |
| `title`, `description`, `category`, `source`, `publisher`, `source_url` | содержание и происхождение |
| `latitude`, `longitude`, `geo_precision` (`source` / `street` / `district` / `city` / `none`) | место. Координаты NULL, если они не обоснованы данными |
| `location_name`, `district` | название места / района |
| `event_time`, `time_precision` (`minute` / `day` / `unknown`) | время **происшествия** (только из данных источника или явных слов в тексте) |
| `published_at` | время публикации источником (NULL, если источник его не даёт) |
| `received_at` | когда мы **впервые** получили запись |
| `updated_at` | когда запись **изменилась у нас** (не трогается, если содержимое то же) |
| `status`, `status_reason`, `expires_at` | актуальность и её обоснование |
| `confidence`, `is_verified`, `severity` | надёжность (0–1), официальный источник, серьёзность |
| служебные | `scope`, `content_hash`, `geocode_attempts`, `miss_count` — наружу не отдаются |

Публичный API отдаёт координаты только при `geo_precision` = `source` или `street`; район и город приходят без точки.

## 3. Правила актуальности (по источникам)

| Источник | Статус при получении | Как заканчивается |
|---|---|---|
| Autobahn warning | `LIVE` — присутствует в текущей официальной ленте | запись пропала 2 запуска подряд → `RESOLVED` |
| Autobahn roadworks / closure | `ACTIVE` | то же. Записи с `future=true` не показываются |
| NINA | `ACTIVE`, пока предупреждение в ленте | пропало 2 запуска подряд или `msgType=Cancel` → `RESOLVED` |
| Presseportal | **всегда** `RECENT` (актуальность неизвестна) | через `PRESS_TTL_HOURS` (12 ч) → `EXPIRED`; старше TTL — сразу `EXPIRED`; релиз старше 7 суток не берётся |

Дополнительные защиты:

- Если запрос по области не удался (например, `A46/warning`), события этой области **не** завершаются: отсутствие ответа ≠ событие закончилось.
- Если не удались все запросы, источник считается упавшим: в `sources` пишется ошибка, `last_success_at` остаётся прежним, а клиент видит, что данные источника «устарели» (`stale` = нет успеха дольше 3 интервалов).
- Статус `LIVE` по «свежему сообщению» не присваивается нигде.
- Публичный запрос дополнительно скрывает записи с истёкшим `expires_at`, даже если cron их ещё не перевёл в `EXPIRED`.

## 4. Время происшествия из текста (`src/time.js`)

Поддерживается: явная дата (`27.09.2026`, `27. September`), `heute` / `gestern` / `vorgestern`, день недели, время `22:55 Uhr` / `gegen 8 Uhr`, часовой пояс Europe/Berlin с учётом перехода на летнее время. Если однозначного указания нет, будущая дата, дата старше 45 дней или «тот же день недели» → `unknown`. Время публикации не подставляется. Всё покрыто тестами.

## 5. Геокодирование (`src/geo.js`)

Только названия улиц из текста; номера домов **не** используются и не сохраняются. Nominatim: User-Agent с вашим контактом, ≤1 запрос/сек, бюджет 3 запроса за запуск, результат (включая «не найдено») кэшируется в D1, оставшееся дообрабатывается в следующих запусках. Результат вне границ города отбрасывается. Улица на карте показывается маркером и штриховой зоной радиусом 160 м с пометкой в карточке, что точный адрес неизвестен.

## 6. Лимиты бесплатной инфраструктуры

Цифры взяты из документации и обзоров на момент разработки и могут измениться: **сверьте их** на developers.cloudflare.com (Workers → Platform → Limits; D1 → Platform → Limits).

- **Workers (free):** ~100 000 запросов/сутки; 10 мс процессорного времени на вызов; до 50 внешних подзапросов на вызов; до 5 cron-триггеров на аккаунт. Нужны 3. Минимальный интервал cron — 1 минута, поэтому «каждые 30–60 секунд» из ТЗ невозможно.
- **D1 (free):** ориентир 5 млн прочитанных и 100 тыс. записанных строк в сутки, 5 ГБ. Из-за ограничений: запись только при изменении содержимого; публичные ответы кэшируются 20–30 с; данные хранятся 30 дней и чистятся. Оценка нагрузки: порядка сотен тысяч прочитанных строк в сутки.
- **10 мс CPU** — самое узкое место. Вызовы источников, ожидание сети и пауза Nominatim не считаются процессорным временем, а разбор небольших JSON и SQL укладывается. Если в логах появятся ошибки «exceeded CPU», уменьшите `AUTOBAHN_ROADS` или перейдите на платный план (от ~5 $/мес).
- **Подзапросы:** Autobahn делает по 3 запроса на каждую автобану в `AUTOBAHN_ROADS` (4 автобаны → 12), плюс обращения к D1. Не добавляйте много автобан без проверки лимита.
- **Cloudflare Cache API** используется для публичных ответов; Workers KV и R2 в MVP не нужны (R2 понадобится для фото пользователей).

Новый источник = один файл в `src/sources/` с функциями `run`/`probe`, строка в `SOURCES` и `CRON_MAP`.

## 8. Масштабирование на другие города

В схеме есть `city_id`, конфиг города вынесен в `src/config.js` (границы, ARS), `sources.scope` изолирует запросы. Для второго города нужно: обобщить `CITY` в список, передавать `city_id` в источники и публичный API, сделать конфиг районов во frontend данными, а не константой. Это сознательно не сделано в MVP, чтобы не усложнять.

## 9. Безопасность и GDPR (что реализовано)

- Все данные выводятся во frontend через `textContent`/DOM (XSS), ссылки источников допускают только http/https; проверено тестом с `<img onerror>` и `javascript:`.
- Все SQL-запросы параметризованы; параметры фильтров проверяются по белым спискам; проверено тестом.
- Админка: Bearer-токен (сравнение за постоянное время, длина ≥16), ограничение частоты и неудачных попыток, ключи API вырезаются из логов.
- CORS по списку `ALLOWED_ORIGINS`; заголовки `nosniff`, `no-referrer`.
- Персональные данные не собираются: нет аккаунтов, нет аналитики, геолокация пользователя не запрашивается; в браузере хранятся только язык и последний кэш событий. Имена пострадавших и номера домов не сохраняются.
- Не реализовано (после MVP): удаление пользовательских данных (нет самих данных), защита от спама в пользовательских сообщениях (нет самой функции).
